## 1. Method

1. **R13 yaml enumeration**: glob `experiments/phase2_round13/*.yaml` → 195 files.
2. **Lane-config extraction per yaml**: light regex parser for the `combined_paired` block. Tracks lane presence, `enabled: true|false`, and `gcs_bucket: ...` for 9 lane names: `teams`, `visomaster_hints_teams`, `proper_data`, `external_training_reals`, `deeplive`, `visomaster`, `visomaster_hints`, `visomaster_teams_enhanced`, `visomaster_enhanced`.
3. **Eval-manifest read**: load `teams_target_domain_manifest_2026-04-23_with_dor.json`, iterate `videos[]`. Extract `split` (dev/lockbox), `label` (real/fake), `frame_paths`, `prefix`, `identity_key`, `source_kind`, `method`.
4. **proper_data manifest read**: same shape, classify by `base_capture_id` (`HDTF*` vs `QCLIP*`).
5. **teams-v2 sample-manifest read**: read 250 cached JSON manifests, extract `original_trimmed_video_name` / `original_original_video_name` / `original_cropped_video_name`, classify.
6. **Substrate classifier** (`classify_video_id_or_path`), precedence order:
   1. exact eval-prefix match (handles 1-char prefixes like `Q`)
   2. HDTF token (`hdtf` substring or `WDA_`/`WRA_`/`RD_` start)
   3. QCLIPS token (`qclip` prefix)
   4. VCD-external (`_vcd_` substring or `real__vcd` start)
   5. embedded YouTube ID pattern `_[A-Za-z0-9_-]{11}\.mp4$`
   6. eval-named-person token (14 substrings: `test_cam`, `cam_test`, `pc_generator`, `bla_bla_chow`, `md_noyn_sharker`, `xiang_xiang2_feng`, `dor`, `xiang`, `roy_d`, `dor_shkedi`, `orel`, `ilan`, `real_dor`, `chikara_takahashi`)
   7. bare 11-char YouTube ID
   8. `other`
7. **Cross-tab**: by `(source_substrate_class, train_lane_or_eval_split)`, frame-weighted and entry-weighted.

## 8. Caveats

- **teams-v2 sampling rate**: 250 of 1,646 sample directories (15.2%) and 250 of 1,346 `complete_pairs` (18.6%). The 100% youtube_origin classification within the sample is uniform across all 10 strategy prefixes (25/25 each). The classification generalizes to the full bucket only under the assumption that no sample outside the 250 carries a non-YouTube `original_trimmed_video_name` / `original_original_video_name`. This assumption is consistent with the prior GCS audit (`GCS_IDENTITY_AUDIT_FACTS_2026-05-12.md` §3) which observed the same anonymization pattern across all 10 strategies but is not exhaustively verified.
- **YouTube-ID pattern false-positive rate**: the 11-character `_[A-Za-z0-9_-]{11}\.mp4$` regex matched 250/250 of the sampled teams-v2 manifests. Inspection of all 25 unique dev identity_keys and 5 unique lockbox identity_keys in the eval manifest showed 0/30 matched the bare 11-character regex on full identity-key strings; substring matching against the embedded `_X{11}.mp4` form is more restrictive than the bare 11-char regex. Estimated false-positive rate on eval substrate: 0/4,664 (0%).
- **Named-token false-positive risk**: the 14 named-person tokens (`test_cam`, `cam_test`, `pc_generator`, `bla_bla_chow`, `md_noyn_sharker`, `xiang_xiang2_feng`, `dor`, `xiang`, `roy_d`, `dor_shkedi`, `orel`, `ilan`, `real_dor`, `chikara_takahashi`) plus the 1-letter `Q` prefix were derived from the observed 25 dev + 5 lockbox identity_keys. The token `dor` is 3 characters and could in principle substring-match unrelated strings; on the 250 sampled teams-v2 manifest bodies, the token `dor` does not appear (per prior GCS audit §4, 23-pattern identity grep returned 0 hits across all 250 manifests).
- **proper_data lane reach in scorecards**: the proper_data lane appears in 102/195 yamls. Whether each yaml actually trained on it depends on `family_weights` (e.g., P8A weight `proper_visomaster_clean_real`/`proper_visomaster_teams_real` not enumerated). The frame-count column reports inventory size of the lane, not the actual sampled frames during training.
- **external_training_reals not enumerated**: the `effort-collected-data` bucket `real/VCD` prefix (configured `max_total_samples: 1200` in P8A) is not directly inspected here; the substrate class for those entries is `vcd_real_external` per the classifier's design but no rows are populated in this audit.
- **The teams-v2 `source` field value `teams_capture`**: this is a field-name collision with the `direct_teams_capture` substrate class used in this audit. The 250/250 teams-v2 manifests carry `source: "teams_capture"` while simultaneously having `original_trimmed_video_name: trimmed_cropped_<YouTubeID>.mp4`. Both statements are true: the per-sample frames in teams-v2 were captured via the Teams capture pipeline (`source: teams_capture`, `pipeline_version: teams_2.0`), but the *underlying source video being played back into Teams* is a YouTube clip (per the `original_*_video_name` fields). This audit's substrate classifier intentionally separates these two concepts; the `direct_teams_capture` class is reserved for content with no upstream YouTube origin (i.e., the eval manifest's named-person frames).
- **dev × `real_identity_passthrough` (50 videos, dor lane)**: per `R13_RLP8_01_unfreeze_clip_codec.yaml` lines 261-267, the bucket `real-teams-dor-roee` is `readout_only_external_real_sources` (NOT loss-bearing during training). These 50 dor videos in the eval manifest's dev split are marked `source_kind: real_identity_passthrough` and `method: dor_real_passthrough`. They are classified as `direct_teams_capture` in this audit (same person, captured-via-Teams).
- The teams-v2 bucket lineage statement is structurally consistent with the bucket metadata: `metadata.json` records `sourced 2026-03-05 via teams-capture pipeline from parent bucket live-deepfake-methods-real-and-fake-frames-cropped` (`analysis/cpu_diagnostics_2026-05-12_gcs_identity_audit/outputs/bucket_metadata.json`). The parent bucket is itself a YouTube-derived deepfake-methods bucket.
