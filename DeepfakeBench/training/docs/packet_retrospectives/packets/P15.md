## Configuration

### Why P15 (per `docs/relaunch_handoffs/P15_GRL_READINESS_NOTE_2026-04-29.md`)

P13 from-scratch + the three indirect anti-shortcut interventions (anchor-aware loss, pipeline-randomization, face scale-jitter) moved the camera-signature shortcut Δ on Axis 3 only directionally (0.66 → 0.52, gate 0.15). The interventions are **input-space perturbations** that pressure the model away from a specific shortcut; the model then finds an adjacent one. P15 adds the **only structurally-different anti-shortcut lever the codebase already supports**: gradient reversal on a quality-domain classifier head (DANN, Ganin 2015). Where P13's interventions perturb inputs and hope the backbone generalizes, GRL **directly penalizes the backbone for producing features that predict the quality domain**. P15 is the cleanest test of "does direct anti-shortcut supervision break the ceiling that input-space anti-shortcut couldn't?"

### Quality-domain mapping (`detectors/effort_detector.py:248-257` + `data/sources/combined_paired.py:66-82`)

| Domain | Sources in P15 training pool |
|---|---|
| 0 clean_academic | `df40` |
| 1 webcam_codec   | `external` (VCD), **`deeplive_teams` (Teams traffic)** |
| 2 studio_capture | `deeplive`, `visomaster` |
| 3 social_media   | (none in training; `youtube` is OOD-monitor only) |

Teams traffic — the same distribution that drives modern_v2 FPR — lands in domain 1. The backbone is penalized whenever its features can identify "this is webcam_codec." That is exactly the shortcut breakdown P13_step18000 demonstrated at τ=0.5 (modern_v2 FPR exploded to 30%+ because the backbone tied "webcam look" to "fake").

### What P15 changes from P14

A single block, five lines of yaml:

```yaml
use_quality_domain_head: true
quality_domain_loss_weight: 0.20    # P10 baseline 0.10 / strong 0.25 mid-bet
quality_domain_require_labels: true
quality_domain_count: 4
quality_head_hidden_dim: 128
```

Everything else identical to P14_FT_FROM_P8A. Seed 1501 (P14 was 737) so wandb runs don't collide.

### Risks / unknowns (per readiness note)

1. **First-ever production exercise of the GRL infrastructure.** Commit `2c9778b` (2026-04-26) added the P10 GRL slate (six yamls drafted with `use_quality_domain_head: true`); none were ever launched. The detector code (`detectors/effort_detector.py:236-274`), the data labels (`combined_paired.py:65-82`), and the trainer loss aggregation (`detectors/effort_detector.py:906-958`) all exist and are unit-tested (`tests/test_unpaired_reals_and_grl.py`), but never run end-to-end on Vertex.
2. **Lambda is static at 0.20.** `GradientReversalLayer.set_lambda(val)` exists but no caller in `trainer/trainer.py` invokes it; ramping λ from 0 → target over warmup steps would require a small trainer patch (~10 lines). Skipping ramp keeps this draft no-code-change. If P15 either crashes from too-strong-too-fast adversarial pressure OR is too weak to bite, P16 should add the ramp.
3. **`quality_domain_require_labels: true`** means samples without a quality_domain label silently skip the GRL loss. All P15 training sources DO emit a label (verified via grep in `combined_paired.py`). Verify in W&B that `train/loss/quality_domain` is non-zero through training; if it's exactly 0, propagation is broken.
4. **wandb-flattening is handled.** `train_sweep.py:322-349` already has fail-fast guards for `use_quality_domain_head`, `quality_domain_count`, `quality_head_hidden_dim`, `quality_domain_loss_weight`. If any propagation breaks, the trainer raises `RuntimeError` immediately. `quality_domain_require_labels` is a top-level bool that wandb passes through cleanly.
5. **The contract policy bug fix is local-only as of this draft.** If P15 is scored via the runner (`arena/run_target_domain_validation_sequential.py`), pass `--promotion_target_fake_recall_min 0.30` (or similar) — otherwise the contract may again pick a τ-degenerate winner. This applies to the upcoming P14 scorecard too.

### Slice-7 reframing of P15's expected gain (from `docs/relaunch_handoffs/TRAINING_EVAL_VISO_BUCKET_GAP_2026-04-29.md` § 3 Implications)

The bucket-gap finding revises the priority ordering: **GRL on training-only pipelines does not teach the model the eval pipeline**, so the modal expected gain on the headline metric is much higher *after* the bucket-gap closes (`R13_P14_DATA_FIX.yaml`) than before. The cleanest sequence per the bucket-gap doc § 6 Recommended action sequence:

1. Move 1 — empirical confirmation (linear probe, ~$0)
2. Move 2 — wire enhanced viso into training (P14_DATA_FIX, ~$70)
3. Move 3 — superpose anti-shortcut interventions on top of P14_DATA_FIX
4. Move 4 — same-identity pair training using proper-data wave
5. Move 5 — only if Moves 2-4 still leave Axis 3 Δ > 0.30: revive P15 GRL with the broader pipeline label set the new data enables

So the canonical Slice-7 framing: **P15 is still useful but is no longer the cheapest next move; it's contingent on P14 verdict + Moves 1-3.**

### Did GRL actually work?

Two questions the readiness note explicitly flagged are answered:

1. **"Did the GRL infrastructure fire live end-to-end?" → YES.** Slot 2's launch logs show `Applied quality-domain head config: enabled=True domains=3 hidden_dim=128 loss_weight=0.2000 require_labels=True`. The first-ever production exercise of the GRL infrastructure (commit `2c9778b`'s P10 GRL slate had drafted six yamls that were never launched). Smoke gate cleared.
2. **"Did GRL catastrophically degrade cross-domain capability?" → NO, the opposite.** `other_fakes_tpr=0.659` was the *highest of the three overnight runs*, beating both jitter-isolated (0.591) and bundle/DATA_FIX (0.020/0.047). The kill-switch concern (viso recall drops > 8pp below P8A) did not need to fire.

The structural success of GRL is the load-bearing piece of evidence here. P15 is the **first run to demonstrate that direct anti-shortcut supervision on a working cross-domain base preserves the cross-domain head room** — an alternative class to P13_FROM_SCRATCH's input-space perturbations.

### Did GRL bite the [CLS] domain manifold? (2026-04-30 afternoon — direct probe)

The canonical DANN test ran the same afternoon (`analysis/domain_confusion_probe_2026-04-30/domain_probe.py`). 3-way logistic regression on frozen [CLS] features predicting `quality_domain`, 5-fold CV, L2-normalized via StandardScaler. The lockbox parquet omits domain 0 (`df40` / clean_academic), so the probe ran 2-way (domain 1 webcam_codec vs domain 2 studio_capture). 300 samples per domain.

| Ckpt | macro-OVR AUC | per-class AUC (d1 / d2) |
|---|---:|---:|
| P8A | 0.9999 | 1.000 / 1.000 |
| **SLOT2_GRL** | **0.9994** | 0.999 / 0.999 |
| SLOT3_JITTER | 0.9969 | 0.997 / 0.997 |

Per the script README's interpretation table, ≤0.55 = GRL worked; ≥0.85 = GRL no-bite. **0.9994 = no-bite by ~7 standard deviations.** GRL @ static λ=0.20 with `quality_domain_loss_weight=0.20` over ~4500 FT steps did NOT collapse the [CLS] domain manifold's discriminability between `webcam_codec` and `studio_capture` — these classes remain near-perfectly separable from a frozen-feature linear probe. The triptych t-SNE (`analysis/embedding_triptych_2026-04-30/outputs/triptych_p8a_slot2_slot3/triptych_grid_tsne.png`) corroborates: SLOT2_GRL's `clip_capture_mode` coloring panel does not show the webcam cluster softening into the rest; the gross arc geometry across all three rows is broadly preserved.

Caveats: (a) the linear probe sees direction-only signals (StandardScaler L2-normalizes); norm-encoded domain info would be invisible. (b) Domain 0 absent → 2-class fallback. webcam_codec vs studio_capture differ at the pixel level so even an untrained CLIP would near-saturate; a no-FT-CLIP control would tell us whether 0.999 is a model property or a data property. That control is not yet run. (c) A non-linear MLP probe could expose residual domain info that the linear head misses; out of scope for this script.

What does this imply for the P15 verdict's reading? The cross-domain TPR not collapsing remains real and load-bearing — that was its own gate, separate from the domain-confusion question. But the second-order claim — *GRL worked at its design intention (collapse the [CLS] domain manifold)* — is now refuted on direct probe. So `value_composite=0.516` for SLOT2_GRL is real, but the *mechanism* is not what the readiness note advertised. The same is true for the slate's leader `mclioexb` — face-size invariance was the design-intent mechanism for jitter@0.50, and direct measurement also refuted that. The night's ranking is robust at the metric level but undiagnosed at the causal level. New thread [`jitter_winner_mechanism_unknown`](../threads/jitter_winner_mechanism_unknown.md) tracks the open puzzle and candidate next probes.

For P16 design: assume GRL's effect at λ=0.20 static is *not* the canonical DANN [CLS]-flattening; it is some other mechanism that nonetheless preserved cross-domain TPR and produced a stability_max of 0.086 (the lowest of the three). If P16 ramps λ from 0 → target as the readiness note proposed, the corresponding closure criterion should explicitly include the linear-probe drop-in-AUC measurement, not just trainer-side `value_composite`. Otherwise P16 risks shipping the same "metric moves, mechanism unclear" outcome.

### Why GRL was second-place to jitter-isolated

The five-line yaml change set GRL on top of the **same bundle** that cost P14_FT 5.7× of its potential value_composite. Slot 2's training included anchor_aware (enabled, weight 5.0), pipeline_randomization (enabled), AND face_scale_jitter at the bundle's 0.25 level. So Slot 2 carries the same bundle drag identified in [`anti_shortcut_bundle_decomposition`](../threads/anti_shortcut_bundle_decomposition.md), plus GRL on top.

The natural follow-up — P16-style — is `P15 + jitter@0.50` (or `P15 - bundle + jitter@0.50`): GRL with ramped λ, anchor_aware + pipeline_random DROPPED, face_scale_jitter at 0.50 instead of 0.25. The expected outcome is a value_composite higher than 0.661 (the jitter-isolated leader) **if** GRL's adversarial supervision and jitter's input-space perturbation are additively useful — not redundant.

### Unexpected: GRL incidentally halved face-size flip rate

The 2026-04-30 afternoon face-size invariance probe found SLOT2_GRL flipped only 22.8% of frames across the tightness sweep, vs P8A baseline 39.4% — i.e., GRL incidentally cut crop-tightness sensitivity by ~42% on production-honest frames despite face-size not being the design-intent target. The slate's *intended* face-size lever (SLOT3_JITTER mclioexb) actually got worse on this metric (43.9%). DATA_FIX (xan4dfto) also incidentally landed at 22.8%. So the empirical face-size-invariance ranking on production-honest 180 frames is **GRL/DATA_FIX > P8A baseline > jitter@0.50 winner** — exactly opposite of the design-intent ordering. This is one of the load-bearing data points feeding [`jitter_winner_mechanism_unknown`](../threads/jitter_winner_mechanism_unknown.md). For P15's reading specifically: GRL's cross-method TPR preservation (0.659, the highest of the three) is consistent with GRL incidentally invariantizing some axis that helps generalization without being the [CLS] domain-confusion advertised mechanism.

## Retrospective (as of 2026-04-29)

P15 is the **only structurally-different anti-shortcut lever the codebase already supports** — every prior shortcut intervention has been input-space (augmentation, FT-from-base, face-scale jitter). GRL on a quality-domain classifier is the cleanest available next class because the data labels exist (`combined_paired.py:65-82`), the detector hooks exist (`effort_detector.py:236-274`), and the unit tests pass (`tests/test_unpaired_reals_and_grl.py`).
