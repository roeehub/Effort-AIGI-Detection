## Configuration

P9 was scoped on the assumption that **P8A is the right base, but trained too aggressively** (`PACKET_9_MID_FLIGHT_HANDOFF_2026-04-26.md:96-104`). Three hypotheses explain P8A's per-method fake-recall regression:

1. **Magnitude** — backbone trained too hot (P9_01 dials `backbone_lr_mult: 0.3` to cap unfrozen-backbone LR at ~9e-6 while keeping head at base 3e-5).
2. **Topology** — `apply_svd_to_mlp` reaches too deep into the visual stack (P9_03 disables it, keeps proj + ln_post unfreeze).
3. **Data** — real/fake codec exposure asymmetry (P9_05 enables `real_codec_uplift: true` so codec aug fires on the real pass too, not only on fake).

Plus two controls:

- **P9_R** — identical to P8A but seed 737 → 938 (replication; P8A is N=1).
- **P9_freeze** — `backbone_lr_mult: 0.0` (zero unfrozen-backbone LR; disentangles magnitude vs topology — what does MLP-SVD buy with native unfreeze frozen?).

All five fork RLP6_04 step 23500. Yaml-only — the `backbone_lr_mult` plumbing landed in `utils/setup.py` via commit `0f2f342` (Slice 5 P8A retro context); the `real_codec_uplift` flag landed in `data/augmentations/pipelines.py` via commit `ebce585`.

### Pre-committed crowning protocol (`PACKET_9_MID_FLIGHT_HANDOFF_2026-04-26.md:134-147`)

A P9 candidate is **promotable** only if all three hold on lockbox:

1. `lockbox_real_fpr ≤ RLP6_04.lockbox_real_fpr` (≤ 0.441%).
2. `lockbox_fake_recall ≥ max(0.80, RLP6_04 − 0.02)` — i.e., ≥21.3% macro.
3. Per-method recall on `deeplive_enhanced ≥ 3.4%` (RLP6_04 6.4% − 3pt slack), `visomaster_enhanced_macro ≥ 0.3%` (RLP6_04 3.3% − 3pt slack).

**Hard cap**: 7% lockbox FPR. Above that, never crown regardless of recall.

**Crown via** `arena/score_teams_promotion_contract.py:430-479` (lexicographic sort), **NOT** by trainer's `value_composite`. This is the first packet whose pre-launch contract names the readout-side gates explicitly and excludes the trainer composite by construction. See [`value_composite_semantics`](../threads/value_composite_semantics.md).

## Conclusions drawn in-session

- **The P9 design space audit (`R13_FULL_STORY_PRE_PACKET_9_2026-04-25.md:213-225`) named the lever set explicitly.** Available knobs at packet design time: independent `unfreeze_*` toggles (proj / ln / mlp-svd), `svd_blocks: [9, 10, 11]`, family weights, codec aug intensity, `quality_domain_loss_weight`, group-DRO, `backbone_lr_mult` (added today, default 1.0). Out of scope: per-method classification loss weighting, asymmetric fake-FN vs real-FN loss, selective per-block weight unfreeze beyond `svd_blocks`. ## Retrospective (as of 2026-04-26)

**Packet is in-flight at end of Slice 5.** The crowning verdict + per-variant readout belongs to Slice 6. What is *certain* at end of Slice 5:

1. **The P9 design is single-variable defensible.** Each of the original 5 variants moves exactly one axis from P8A; the longshot pack is honest about being exploratory. The variants together can disentangle the three hypotheses (magnitude / topology / data) provided the lockbox readouts produce stable separations.
2. **The pre-committed crowning protocol is the first one to cleanly exclude `value_composite`.** Whatever P9 produces, the rule is "lockbox per-method recall floors gate the promotion; `value_composite` is monitoring."
3. **Two structural bugs that affect P9 attribution were discovered + fixed during P9 in-flight**: the in_proj-SVD silent gradient bug (commits `2feea58` / `7af72b1`) and the wandb artifact-name length bug (commit `f366368`). The first means P9 variants launched before the fix carry an imprecise attribution baseline; the second is hygiene that doesn't change measurements.

**What might overturn the packet** (per `PACKET_9_MID_FLIGHT_HANDOFF_2026-04-26.md:104-105, 158-160`):

- If Roee's new evidence (held back at handoff time) invalidates the P8A premise — e.g., the FPR win is a measurement artifact, or the per-method regression is fundamental and not softening-recoverable, or there's a different shortcut hiding in P8A — then P9 was solving the wrong problem.
- If no P9 candidate beats RLP6_04 on the crowning protocol, the P8A "soften" thesis is questionable; the P9 slate may have been the wrong investigation.
- If a P9 candidate looks like a clean winner: do not promote yet. The handoff is explicit that the user holds final pick.

**Retroactive in_proj-SVD correction.** Every P9 variant launched before image 1.3.216 (commit `ac83ba1`, 2026-04-26 21:15 UTC) ran with `apply_svd_to_in_proj: true` but zero gradient on the q/k/v residuals. The Phase C overnight slate (P10_SYM-on-P8A C.1 vs C-ablation) tied within noise on the post-fix code, suggesting in_proj-SVD does not materially move the canonical configuration. Implication for P9 attribution: the per-variant deltas measured during P9 in-flight were under broken-bug conditions for the original 5; if any variant becomes load-bearing in Slice 6's readout, a re-run under the post-fix code path may be warranted to validate.

**Preprocessing-parity note.** P9 scorecard numbers will be **post-fix** (commit `855871e`).
