## Eval-substrate caveats (added 2026-04-29 afternoon)

A post-Slice-7 visual audit of the very-sharp-FP and is_no_face slices (the two "open follow-ups" from the 2026-04-27 lockbox-dev property investigation in `~/Documents/repos/vault/wiki/ml-training/investigations/`) discovered three issues with the eval substrate that bear on how every FPR / recall number below should be read:

1. **Eval-vs-production crop-tightness mismatch** (structurally upstream of the shortcut and FPR investigations the wiki already tracks; see [`eval_production_crop_tightness_gap`](threads/eval_production_crop_tightness_gap.md)) — eval frames carry more background context around the face than production crops do. Any failure mode that depends on background content (camera/ISP signature, codec ringing, virtual-background objects) is amplified in eval relative to production. **Implication**: translation from eval FPR to production FPR is suspect for background-driven failure modes; the close criterion of `shortcut-deployment-block` is measured on eval and its production translation is now a separately-open question.

2. **`sharpness_laplacian` is computed on the full image, not the face** (`analysis/lockbox_tagging/layers/quality.py:82`; see [`sharpness_metric_bug`](threads/sharpness_metric_bug.md)) — the metric conflates face sharpness with non-face content sharpness. The 2026-04-27 investigation's "very sharp (>402): 45% FPR" finding now mixes two populations (genuinely sharp faces in sharp environments vs soft faces in tiny / busy / compressed crops where non-face content drives the laplacian). **Implication**: any per-quartile FPR analysis indexed on `sharpness_laplacian` is partially confounded.

3. **Eval substrate has known data-quality issues** (see [`eval_substrate_data_hygiene`](threads/eval_substrate_data_hygiene.md)) — (a) the is_no_face slice (n=219) is data degeneracy where MediaPipe's "0 faces" verdict is correct, not a model-weakness signal; (b) the eval substrate contains 99×110-pixel source crops (e.g., `PC_Generator__s15_1754.4_frame_058496_crop_002__d83b853d.jpg`) that pass the existing `face_pixel_area > 1k` floor but fail any reasonable source-resolution bound like `min(width, height) >= 200`. **Implication**: a source-image-resolution floor is a parallel cut to the existing face-area filter; the modern_lockbox_v2 build does not currently apply it.

**All FPR numbers in the headline-metrics section below should be read with these caveats.** Modern_lockbox_v2 already excludes is_no_face (so the v2 0.71% FPR is unaffected by the is_no_face finding), but v2 does **not** apply a source-image-resolution floor and v2's filter set does not address the crop-tightness gap. The `shortcut-deployment-block` close criterion is measured on the eval substrate and its production translation is now an open variable. **None of this changes the contract-recall reframing** (frame-level AUCs are computed directly on cached predictions, with all of the same eval-substrate caveats applied uniformly across baseline-vs-corrected-policy comparisons). What it does change is: **a future agent who reads "the model has eval-FPR X" should not treat X as a production-FPR floor without auditing the eval-vs-production crop-tightness delta.**
